# Redis connection and key workspace

NyaDB now supports standalone Redis 7 or later through a registered neutral runtime provider. Redis 7.4 fixtures exercise TCP and certificate-verified TLS, a named ACL user, the common grid, native commands and session revocation.

## Connection and identity

The enabled Redis chooser card opens the common connection editor. Profiles store host, port (6379 by default), database index, optional ACL username, connection timeout, pool/query limits, TLS mode, CA file and optional certificate server name. Passwords remain transient or in the existing credential vault. `redis://` and `rediss://` imports keep passwords outside the profile and reject unsupported URI options. Versioned local storage preserves other engines and applies defaults to older empty Redis option records.

Only standalone servers are accepted. The adapter checks Redis version and cluster mode. Database namespaces use the raw index as their catalog identity. `CONFIG GET databases` is optional: if ACLs deny it, navigation exposes the configured database. Database discovery is capped at 256 and live database pools at 64. Each database has one `keys` object backed by the sole shared dataworkspace State/Document and grid.

## Values, browsing and editing

The grid columns are `key`, `type`, `ttl_ms` and `value`. Raw keys and every byte string in typed value JSON use canonical base64; binary keys, fields and values round-trip without UTF-8 conversion. String values use `{"string":"base64"}`; other types use `hash` pairs, `list`/`set` members, `zset` member/score records, and `stream` ID/field records. The column metadata explains this format. Stream IDs and sorted-set scores stay plain text; scores accept signed infinity and reject NaN. New stream entries accept 1–254 field pairs; adding larger entries requires native commands.

Browsing uses bounded `SCAN MATCH`, an authenticated cursor and pending keys. Key filters accept base64: equality and substring modes quote Redis glob metacharacters; the `like` mode intentionally uses a decoded Redis glob. Unsupported SQL filter combinations and sorting are rejected. One page deduplicates its keys; SCAN is not a stable snapshot, so changes during traversal can still yield duplicates or omissions across pages. Counts use DBSIZE and ignore filters. Deep arbitrary jumps beyond 10,000 keys require a retained cursor.

Complete edits and streamed exports require supported values within the 1 MiB editing limit. Oversized values receive bounded previews and cannot be silently truncated into an edit. String field reads retrieve only the byte range needed for at most 1024 characters of the typed JSON/base64 representation. Full composite value editing remains explicitly bounded. Native replies are bounded to 1 MiB of wire data, 1000 elements per array and 32 levels of nesting; their grid preview shows at most 1024 characters.

Insert, update, delete and rename reuse the common draft/save/verification lifecycle. A signed original snapshot qualifies the key by profile, database, object and session; its fingerprints retain both value and expiry checks. Updates compare the original DUMP bytes and PEXPIRETIME in the same script. Omitting `ttl_ms` preserves absolute expiry; `-1` makes a key persistent and a positive value sets a new TTL using server time. Expired or concurrently changed keys conflict; renaming never overwrites an existing destination.

The adapter validates the batch before writes, builds an isolated temporary value, and publishes it only after its commands succeed. A server script error does not imply rollback: partial or uncertain results retain drafts and forbid replay. Verification distinguishes observed applied, not applied and indeterminate states. Successful saves capture the committed DUMP bytes for the next edit. Untouched hash fields retain their expiration state. Stream edits restore the original serialized stream, append new explicit IDs and delete removed entries, retaining consumer groups and their metadata. Existing stream IDs cannot be rewritten; Redis validates that appended IDs exceed the stream's last generated ID.

## Native commands and lifecycle

A command document accepts a CLI line with quotes/escapes or a JSON argument array. An argument object `{"base64":"..."}` carries arbitrary bytes; formatting preserves these arguments. Explicit selection wins, otherwise the caret selects one CLI line or the complete JSON array.

Each query lease owns one physical RESP2 socket. MULTI/WATCH state remains on that socket; changing the UI database while that state is active is rejected. Neither pooled grid writes nor native commands retry automatically. Cancellation closes the owning socket and waits for the network operation to return; further commands require explicit session replacement. Disconnect preserves command text and requires recovery of its original profile, with no replay. Published runtime generations revoke captured reads, writes and query leases.

Pub/Sub, MONITOR, protocol/socket ownership changes, Cluster and Sentinel need separate interaction/routing support and are rejected. SQL generation/export/import, SQL EXPLAIN, relational table designers, administration and backup/restore are not advertised for Redis.

## Reproducible verification

Run `/usr/bin/python3 tools/verify_redis_fixture.py` for TCP and TLS fixtures, or set `NYADB_REDIS_RACE=1` for the same real-server tests under the race detector. The verifier creates unique loopback-only Redis containers and temporary ACL/TLS files, then removes only its own fixtures. It never uses an existing Redis service. Direct integration tests require `NYADB_REDIS_IT=1` plus explicit fixture credentials and loopback port.

Fixture checks cover all six types, binary values, TTL preservation, concurrent conflicts, rename/delete, stream consumer groups, invalid batch rejection, SCAN traversal/cursor validation, oversized values and bounded field reads, ACL failure, TLS hostname rejection, stable physical query connections, transactions, blocking cancellation, session generations and the real shared-grid/native-command UI workflow. Captures in ignored `build/redis/` come from headless MyGo testing and do not establish native-window verification.

Validation completed with Go 1.27.3 and the pinned MyGo fork (`GOWORK=off`):

- `CGO_ENABLED=0 go test ./...` passed.
- Race tests passed for contract, command parsing, connections, local storage, runtime, Redis and all affected UI modules; the existing full shell race suite completed in 549 seconds. Final Redis service tests and real TCP/TLS fixtures also passed under `-race`, including cancellation during an unresponsive authentication handshake.
- `go vet ./...`, `go tool mygo vet` and `go tool mygo i18n check` passed; catalogs were regenerated through MyGo tooling.
- `/usr/bin/python3 -m unittest discover -s tests -v` passed all 67 tests.
- Linux amd64, Windows amd64 and macOS arm64 builds passed with `CGO_ENABLED=0`.

The disposable fixtures and their ACL/TLS material were removed after verification. The headless grid capture and logs remain in ignored `build/redis/` for local review.
